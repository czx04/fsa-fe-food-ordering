# 3.3.2. Thiết kế và hiện thực cơ chế Realtime WebSocket

> **Phạm vi khảo sát:** Báo cáo được xây dựng từ `server/src/socket.ts`, `server/src/services/socketService.ts`, `server/src/services/orderService.ts`, `server/src/index.ts`, `client/src/services/socketService.ts`, `client/src/pages/OrderDetailPage.tsx` và các controller vận hành đơn hàng. Repository sử dụng Socket.IO trên namespace mặc định, không có namespace riêng cho merchant.

> **Quy ước trạng thái:** Code hiện tại sử dụng `pending`, `confirmed`, `preparing`, `delivering`, `delivered`, `cancelled`. Trong đó `confirmed` tương đương `ACCEPTED`, còn `delivered` tương đương `COMPLETED` trong yêu cầu nghiệp vụ. Vì vậy, tài liệu giữ nguyên tên trạng thái trong mã nguồn và ghi chú ánh xạ khi cần.

## 1. Khái niệm & Đặt vấn đề

Trong nền tảng giao nhận đồ ăn, trạng thái đơn hàng thay đổi theo thời gian thực: khách hàng cần biết nhà hàng đã tiếp nhận đơn, đang chuẩn bị hay đã bàn giao cho người giao; phía merchant cần nhận được thay đổi và cập nhật trạng thái vận hành. Nếu chỉ dùng HTTP Polling, client phải gửi request lặp lại dù trạng thái chưa thay đổi. Chu kỳ polling càng ngắn thì độ trễ càng thấp nhưng số request, chi phí CPU, connection và băng thông càng lớn; chu kỳ dài lại làm trạng thái hiển thị chậm.

WebSocket/Socket.IO giải quyết bài toán bằng một kết nối hai chiều lâu dài. Server chỉ phát sự kiện khi có thay đổi, giảm số request không cần thiết và cho phép client cập nhật giao diện gần như ngay sau khi `Order` được ghi thành công. Tuy nhiên, realtime không tự bảo đảm tính đúng đắn dữ liệu: kết nối có thể mất, event có thể đến trước khi client khôi phục phiên, và room phải được kiểm tra quyền truy cập để tránh lộ thông tin đơn hàng.

Các yêu cầu kỹ thuật chính:

- Chỉ khách hàng sở hữu đơn hoặc merchant quản lý nhà hàng tương ứng được tham gia kênh của đơn.
- JWT phải được kiểm tra trong WebSocket handshake, không tin `userId` do client tự gửi.
- Khi mất kết nối, client phải tự reconnect, join lại room và gọi REST để lấy trạng thái chuẩn mới nhất.
- Server phát event có mục tiêu tới room đơn hàng và room merchant, tránh broadcast toàn bộ hệ thống.
- Cập nhật trạng thái phải được lưu database trước khi phát event để event không mô tả dữ liệu chưa commit.

### 2.2. Quản lý Namespace, Room và quyền truy cập

#### Namespace và room hiện tại

- Socket.IO khởi tạo bằng `new Server(server, ...)`, tức sử dụng namespace mặc định `/`.
- Client kết nối tới `VITE_SOCKET_URL` hoặc `http://localhost:3000` ở development.
- Khi mở trang chi tiết đơn, client phát `join:order` với `orderId`.
- Server đọc `Order.findById(orderId)` và chỉ gọi `socket.join(\`order:${orderId}\`)` nếu:
  - `order.customerId` trùng với `socket.data.user._id`; hoặc
  - `order.restaurantId` trùng với `socket.data.user.restaurantId`.
- Server phát `order:updated` tới:
  - `order:{orderId}`: kênh riêng cho khách hàng và merchant đã join.
  - `restaurant:{restaurantId}`: kênh tổng hợp cho dashboard nhà hàng, nhưng hiện chưa có code join room này.

#### JWT handshake

Client truyền token ở trường `auth` của Socket.IO:

```ts
io(SOCKET_URL, {
  reconnection: true,
  reconnectionAttempts: 5,
  reconnectionDelay: 1000,
  auth: { token: this.token },
})
```

Server xác thực trước khi phát sự kiện `connection`:

```ts
io.use(async (socket, next) => {
  const token = socket.handshake.auth.token
  if (!token) return next(new Error('Authentication error: Token not provided'))

  const decoded = verifyAccessToken(token)
  if (!decoded) return next(new Error('Authentication error: Invalid token'))

  socket.data.user = await User.findById(decoded.userId).lean()
  next()
})
```

Trong production nên kiểm tra thêm `deletedAt`, `status !== 'locked'`, role và tồn tại của `restaurantId` trước khi chấp nhận socket. Hiện middleware lưu toàn bộ user document vào `socket.data.user`; nên giới hạn projection (`_id`, `role`, `restaurantId`, `status`) để giảm dữ liệu trong bộ nhớ socket.

### 2.3. Danh mục sự kiện Socket

**Bảng 3.4: Danh mục sự kiện Socket.IO của phân hệ đồng bộ trạng thái đơn hàng**

| Event Name | Emitter | Listener | Payload Data Structure |
| --- | --- | --- | --- |
| `connection` | Socket.IO server | Server callback `io.on('connection')` | `Socket`; server sử dụng `socket.id` và `socket.data.user`. |
| `connect` | Socket.IO client | `OrderDetailPage.handleConnect` | Không có payload. Client phát `join:order` và gọi REST lấy dữ liệu mới nhất. |
| `connect_error` | Socket.IO client | `OrderDetailPage.handleConnectError` | `Error`; client ghi log và hiển thị thông báo lỗi realtime. |
| `join:order` | Client | Server `socket.on('join:order')` | `orderId: string`; server kiểm tra quyền trước khi join `order:{orderId}`. |
| `order:updated` | `emitOrderUpdate` trên server | Client `OrderDetailPage.handleOrderUpdate`; merchant dashboard có thể subscribe | `OrderDetail`, gồm `_id`, `orderStatus`, `statusHistory`, `pricing`, snapshots, items và timestamp. |
| `disconnect` | Socket.IO server/client | Server log callback; Socket.IO client tự xử lý reconnect | Không có payload nghiệp vụ; có thể có lý do disconnect ở API Socket.IO. |
| `join:restaurant` | Chưa triển khai; khuyến nghị bổ sung | Merchant dashboard và server | `restaurantId: string`; server phải kiểm tra `socket.data.user.restaurantId` trước khi join `restaurant:{restaurantId}`. |
| `order:resync` | Chưa triển khai; khuyến nghị bổ sung | Client sau reconnect hoặc server | `{ orderId: string }`; có thể thay thế bằng REST `GET /api/orders/:id` như hiện tại. |

Payload `order:updated` hiện là toàn bộ `OrderDetail`, không phải delta nhỏ. Điều này đơn giản hóa việc cập nhật UI nhưng có thể tăng kích thước event khi đơn có nhiều item hoặc `statusHistory` dài. Khi tải lớn, có thể chuyển sang payload delta gồm `orderId`, `previousStatus`, `orderStatus`, `changedAt`, `changedByRole` và yêu cầu client dùng REST khi cần chi tiết.

### 2.4. Phát thông báo và cập nhật trạng thái

Các service cập nhật trạng thái theo thứ tự: kiểm tra trạng thái hợp lệ, cập nhật document `Order`, `save()`, đọc lại `OrderDetail`, sau đó gọi `emitOrderUpdate`. Ví dụ, `updateOrderStatusByOwner` cho phép:

- `pending` → `confirmed` hoặc `cancelled`;
- `confirmed` → `preparing` hoặc `cancelled`;
- `preparing` → `delivering`;
- `delivering` → `delivered`.

`cancelOrder` của khách hàng chỉ cho phép hủy khi trạng thái là `pending`. Việc gọi `emitOrderUpdate` sau `await order.save()` là đúng hướng vì event chỉ được phát sau khi dữ liệu đã ghi thành công. Tuy nhiên, nếu hai tác nhân đồng thời đọc cùng một trạng thái rồi cùng `save()`, kiểm tra chuyển trạng thái hiện tại chưa phải một cập nhật điều kiện nguyên tử; nên chuyển sang `findOneAndUpdate` với điều kiện `orderStatus` cũ và `$push` lịch sử trong cùng thao tác.

Mã nguồn hiện tại:

```ts
const updatedOrder = await orderRepository.findOrderById(orderId) as OrderDetail
emitOrderUpdate(updatedOrder)
```

Mã giả thiết lập room merchant và phát targeted event:

```ts
io.use(async (socket, next) => {
  const token = socket.handshake.auth?.token
  const decoded = token ? verifyAccessToken(token) : null
  if (!decoded) return next(new Error('Authentication error'))

  const user = await User.findOne({
    _id: decoded.userId,
    deletedAt: null,
    status: { $ne: 'locked' },
  }).select('_id role restaurantId').lean()

  if (!user) return next(new Error('Authentication error'))
  socket.data.user = user
  next()
})

io.on('connection', (socket) => {
  socket.on('join:order', async (orderId: string) => {
    const order = await Order.findById(orderId).select('customerId restaurantId').lean()
    const user = socket.data.user
    const isCustomer = order?.customerId.toString() === user._id.toString()
    const isMerchant = order?.restaurantId.toString() === user.restaurantId?.toString()

    if (order && (isCustomer || isMerchant)) {
      await socket.join(`order:${orderId}`)
    }
  })

  socket.on('join:restaurant', async (restaurantId: string) => {
    const user = socket.data.user
    if (user.role === 'restaurant_owner' &&
        user.restaurantId?.toString() === restaurantId) {
      await socket.join(`restaurant:${restaurantId}`)
    }
  })
})

function emitOrderUpdate(order: OrderDetail) {
  const io = getIoInstance()
  const payload = {
    orderId: order._id,
    orderStatus: order.orderStatus,
    statusHistory: order.statusHistory,
    updatedAt: order.updatedAt,
  }

  io.to(`order:${order._id}`).emit('order:updated', payload)
  io.to(`restaurant:${order.restaurantId}`).emit('order:updated', payload)
}
```

Đoạn mã trên là hướng dẫn triển khai, không phải thay đổi code trong phạm vi báo cáo. Cần chống room enumeration bằng cách trả cùng một kết quả im lặng hoặc lỗi tổng quát khi `orderId` không tồn tại/không có quyền; không gửi thông tin nhà hàng hoặc khách hàng trước khi hoàn tất authorization.

### 2.5. Mất kết nối và reconnect

Client hiện cấu hình:

- `reconnection: true`;
- tối đa `5` lần thử;
- khoảng chờ ban đầu `1000 ms`;
- không disconnect socket khi rời `OrderDetailPage`, chỉ gỡ listener để tái sử dụng kết nối.

Sau mỗi `connect`, `OrderDetailPage`:

1. Phát lại `join:order(id)` vì room membership không nên được giả định còn nguyên sau reconnect.
2. Gọi `GET /api/orders/:id` để lấy trạng thái chuẩn mới nhất.
3. Đăng ký `order:updated`.

Đây là mô hình **eventual consistency có resynchronization**: event giúp UI cập nhật nhanh, còn REST là nguồn khôi phục khi event bị bỏ lỡ trong khoảng mất mạng. Nếu reconnect thất bại sau 5 lần, UI hiển thị lỗi realtime nhưng vẫn có thể cung cấp nút refresh hoặc polling thưa làm fallback.

Khi JWT hết hạn trong lúc socket đang kết nối, client cần cập nhật `socket.auth.token` bằng access token mới và gọi `socket.connect()` lại; nếu refresh token thất bại, `AuthContext` hiện phát hiện session hết hạn, xóa token và gọi `socketService.setAuthToken(null)`.

## 3. So sánh & Đánh giá (Mục 3.4)

### 3.1. So sánh WebSocket, Polling và Long-polling

Các con số dưới đây là **mục tiêu/ước lượng kiến trúc cho một payload trạng thái nhỏ**, không phải benchmark đã chạy trong repository. Kết quả thực tế phụ thuộc vùng mạng, số kết nối, kích thước payload, MongoDB và cấu hình reverse proxy.

**Bảng 3.5: So sánh định lượng và định tính các cơ chế đồng bộ trạng thái**

| Tiêu chí | WebSocket/Socket.IO | HTTP Polling | HTTP Long-polling |
| --- | --- | --- | --- |
| Độ trễ trạng thái mục tiêu | Khoảng 50–150 ms sau khi server phát event | Bằng chu kỳ polling, ví dụ 2–5 giây | Khoảng 100–500 ms sau khi event xuất hiện, phụ thuộc timeout |
| HTTP header overhead | Handshake ban đầu; sau đó frame nhỏ, thấp | Lặp lại đầy đủ request/response header ở mỗi chu kỳ | Header lặp lại sau mỗi response/timeout |
| Request khi không có thay đổi | Gần như 0 ở application layer | Cao, mỗi client gửi request định kỳ | Thấp hơn polling nhưng vẫn phải giữ request mở và tái lập |
| CPU server | Thấp hơn khi event thưa; cần quản lý connection | Tăng theo số client × tần suất polling | Tăng do nhiều request chờ và timeout |
| RAM server | Giữ state connection/socket và room membership | Ít state kết nối lâu dài | Giữ nhiều request pending, có thể tăng RAM |
| Khả năng cập nhật hai chiều | Có | Không tự nhiên, cần request riêng | Không tự nhiên, cần request riêng |
| Xử lý reconnect | Socket.IO hỗ trợ reconnect; ứng dụng phải rejoin/resync | Request tiếp theo tự khôi phục | Client phải xử lý timeout và gửi request mới |
| Độ phức tạp triển khai | Cao hơn: auth handshake, room, scale-out adapter | Đơn giản | Trung bình |
| Phù hợp với trạng thái đơn hàng | Phù hợp nhất | Fallback đơn giản | Fallback khi WebSocket bị chặn |

### 3.2. Ưu điểm, hạn chế và khả năng mở rộng

Ưu điểm của implementation hiện tại:

- JWT được xác thực trước `connection`, giảm nguy cơ socket ẩn danh.
- Room theo `orderId` giới hạn phạm vi event và hỗ trợ targeted delivery.
- Event được phát sau khi `Order.save()` hoàn tất.
- Client gọi REST sau reconnect, giảm nguy cơ UI giữ trạng thái cũ.
- Socket service tái sử dụng một kết nối trong frontend, tránh mở socket mới khi điều hướng.

Hạn chế cần khắc phục:

- Room `restaurant:{restaurantId}` được emit nhưng chưa có listener `join:restaurant` trong server; merchant có thể không nhận event nếu chưa join room `order:{orderId}`.
- Server middleware chưa kiểm tra `deletedAt`, trạng thái khóa và quyền role đầy đủ.
- Không có acknowledgement/error response rõ ràng cho `join:order`; client không biết join thất bại.
- Reconnect tối đa 5 lần nhưng chưa có backoff jitter, chưa có trạng thái `reconnecting/reconnected` rõ ràng và chưa có fallback polling tự động.
- Event gửi toàn bộ `OrderDetail`, gây overhead khi lịch sử đơn lớn.
- Chưa có Socket.IO adapter dùng Redis hoặc message broker; khi scale nhiều instance, socket ở instance A không tự phát tới client ở instance B.
- Cập nhật trạng thái chưa có optimistic locking/conditional update nên event có thể phản ánh kết quả của một race-condition nghiệp vụ.

### 3.3. Fallback và bảo đảm State synchronization

Fallback khuyến nghị khi client rớt mạng:

1. Giữ dữ liệu đơn cuối cùng trong UI và hiển thị nhãn `Đang kết nối lại`.
2. Thử reconnect với exponential backoff có jitter, ví dụ 1 s, 2 s, 4 s, 8 s, giới hạn tối đa.
3. Khi `connect` thành công, rejoin tất cả room và gọi REST `GET /api/orders/:id`.
4. Nếu WebSocket thất bại liên tục, chuyển sang polling thưa 15–30 giây cho các đơn chưa terminal (`delivered`, `cancelled`).
5. Dừng polling khi socket hoạt động hoặc đơn đã ở trạng thái kết thúc.
6. Khi server phát event, so sánh `updatedAt` hoặc sequence number để bỏ qua payload cũ đến muộn.

Trong triển khai nhiều instance, cần dùng Redis adapter hoặc broker tương đương để đồng bộ room/event giữa các process. Khi đó, MongoDB vẫn là nguồn dữ liệu chuẩn; Socket.IO chỉ là kênh phân phối thông báo. Nếu event bị mất, client luôn có thể khôi phục bằng REST, do đó tính đúng đắn không phụ thuộc tuyệt đối vào delivery của WebSocket.

Kết luận, Socket.IO phù hợp hơn HTTP Polling cho bài toán đồng bộ trạng thái đơn hàng vì giảm latency và request thừa. Implementation hiện tại đã có nền tảng JWT handshake, room theo order và reconnect/resync ở client; các bước ưu tiên tiếp theo là hoàn thiện room merchant, authorization projection, acknowledgement, fallback polling và adapter dùng chung khi scale ngang.
